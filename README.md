# 医疗病历智能辅助 Agent

面向住院医生查房场景的病历智能辅助系统原型。系统通过模拟医院内部患者数据、查房记录和医生权限，演示从患者信息查看、查房记录采集，到病程记录生成、医生审核签字和病历上传的完整流程。

> 本项目当前为教学、研究和产品原型用途，不连接真实医院内网，不用于真实诊疗，也不能替代医生的临床判断。

## 项目背景

住院医生每天需要查房，并将患者当日的症状、体征、检查结果、治疗反应和后续计划整理到病历中。该工作重复性高、耗时长，也容易受到信息分散、遗漏和录入错误的影响。

本项目希望探索一种“病历副驾驶”模式：

- 医生通过账号访问自己权限范围内的患者信息；
- 查房时记录或输入本次查房内容；
- Agent 结合患者既往病历、诊断、用药和检验结果，提取本次病情变化；
- 自动生成日常病程记录草稿和待确认提醒；
- 医生审核、修改并完成最终签字后，才允许写入病历系统。

## 核心目标

第一阶段先完成一个可运行的模拟 MVP，验证以下完整链路：

```text
医生登录
  → 查看负责患者
  → 查看患者病历信息
  → 开始查房并录入模拟语音
  → 提取关键病情事实
  → 生成日常病程记录草稿
  → 医生审核和修改
  → 模拟电子签名并上传病历
```

## 当前 MVP 范围

- 模拟医生账号和权限；
- 模拟患者、诊断、用药、检验和历史病程数据；
- 患者列表和患者详情查看；
- 模拟查房文本录入（后续可接入医学语音识别）；
- 病情事实结构化展示；
- 日常病程记录草稿生成；
- AI 草稿与医生最终版本分开保存；
- 医生审核、确认、签名和上传状态模拟；
- 访问、生成、修改和签名操作的审计记录。

当前版本不包含：真实医院内网接入、真实患者数据、自动诊断、自动开医嘱、自动修改最终病历以及无需医生确认的医疗决策。

## 产品原则

### 医生最终负责

Agent 只生成辅助草稿、摘要和提醒。病历必须经过医生审核、修改和电子签名后才能成为最终记录。

### 有依据才生成

系统不应根据模板臆造未被记录的体征、检验结果、诊断或治疗计划。无法确定的信息需要标记为“待确认”。

### 最小权限

医生只能访问其当前权限范围内的患者。后续接入医院系统时，应使用医院统一身份认证和细粒度权限控制，而不是共享高权限账号。

### 全流程可追溯

保留原始查房文本、结构化事实、AI 草稿、医生修改内容、最终病历和签名记录，便于审核、回溯和问题定位。

## 推荐系统架构

```text
┌──────────────┐
│ 医生工作台    │  患者列表、病历查看、查房录入、审核签名
└──────┬───────┘
       │
┌──────▼───────┐
│ 业务 API 层   │  权限、患者、查房会话、病历和审计接口
└──────┬───────┘
       │
┌──────▼────────────────┐
│ 医疗数据与 Agent 服务  │  事实抽取、时间线整理、规则校验、草稿生成
└──────┬────────────────┘
       │
┌──────▼───────┐
│ 模拟数据库    │  医生、患者、诊断、用药、检验、病历和操作日志
└──────────────┘
```

未来接入真实医院系统时，可将模拟数据库和接口替换为 HIS、EMR、LIS、PACS 等系统的合规接口，前端工作流尽量保持稳定。

## 数据模型概览

建议至少包含以下实体：

- `doctors`：医生账号、科室和角色；
- `patients`：患者基本信息、床号和住院信息；
- `diagnoses`：诊断及诊断时间；
- `medications`：当前及历史用药；
- `lab_results`：检验项目、数值、单位和时间；
- `medical_records`：历史及最终病程记录；
- `rounding_sessions`：一次查房会话及原始查房文本；
- `generated_drafts`：结构化事实、AI 草稿、医生修改稿和签名状态；
- `audit_logs`：访问、生成、修改、签名和上传操作。

## 推荐技术栈

技术栈可以根据开发者熟悉程度调整。快速实现原型时可采用：

- 前端：React + TypeScript + Ant Design；
- 后端：FastAPI；
- 数据库：SQLite；
- ORM：SQLAlchemy；
- Agent/生成模块：先使用规则和模拟结果，之后再接入大模型；
- 部署：本地开发或院内隔离环境模拟。

## PostgreSQL 后端接入

项目已提供一个 FastAPI + PostgreSQL 后端示例，位于 [`backend/`](F:/health_agent/backend/)。前端会优先请求 `http://127.0.0.1:8000/api` 的病历接口；当后端不可用时，会自动回退到页面内的虚构演示数据。

快速启动步骤：

```powershell
Copy-Item .env.example .env
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend/requirements.txt
uvicorn backend.main:app --reload --port 8000
```

启动前请在 `.env` 中填写自己的 `DATABASE_URL`，并先在 PostgreSQL 中创建对应数据库。开发环境可调用 `POST /api/dev/seed` 写入虚构医生、患者和病历数据，接口文档位于 <http://127.0.0.1:8000/docs>。真实医院数据接入前必须补充统一身份认证、细粒度权限、审计日志、加密和迁移管理。

如果更熟悉 Vue 或 Node.js，也可以替换前后端框架；项目重点是验证业务流程、数据边界和医生审核体验，而不是绑定某一种技术栈。

## 开发路线

### 阶段一：完成静态交互原型

实现医生登录、患者列表、患者详情、查房记录、病程草稿和审核签名页面。

### 阶段二：接入模拟后端和数据库

让患者数据、查房记录、AI 草稿、医生修改稿和签名状态可以持久化保存。

### 阶段三：实现结构化事实抽取

先用规则从预设查房文本中提取症状、体征、检验趋势和治疗反应，验证前后端数据结构。

### 阶段四：接入大模型生成草稿

要求模型输出结构化 JSON，再由系统渲染页面。生成内容应尽量关联原始查房文本和患者数据来源。

### 阶段五：增加校验和审计能力

增加患者身份匹配、数值和单位检查、药物一致性检查、未确认内容提醒，以及完整的操作日志。

### 阶段六：模拟真实医院接口

通过接口适配层模拟 HIS、EMR、LIS、PACS 数据源，为未来合规接入医院内网做准备。

## API 规划

后端可以围绕以下接口组织：

```text
GET  /api/patients
GET  /api/patients/{id}
GET  /api/patients/{id}/medications
GET  /api/patients/{id}/labs
GET  /api/patients/{id}/records
POST /api/rounding-sessions
POST /api/medical-records/generate
PATCH /api/medical-records/{id}
POST /api/medical-records/{id}/sign
GET  /api/audit-logs
```

接口命名仅用于原型规划，实际实现时需要结合认证、权限和数据校验设计。

## 示例查房输入

```text
患者今日精神状态尚可，诉咳嗽较前减轻，无明显胸闷气促，
夜间体温最高 37.2℃。查体：双肺呼吸音稍粗，未闻及明显干湿性啰音。
今日复查血常规，白细胞较昨日下降。
```

预期提取结果包括：

- 症状变化：咳嗽较前减轻；
- 阴性症状：无明显胸闷气促；
- 生命体征：体温最高 37.2℃；
- 查体结果：双肺呼吸音稍粗，未闻及明显干湿性啰音；
- 检验趋势：白细胞较昨日下降；
- 待确认项：如果原始记录缺少治疗计划，不应由 Agent 自动补写。

## 安全与合规说明

本项目使用的患者数据应全部为虚构数据或经过严格脱敏的数据。禁止将真实患者信息直接提交给未经医院批准的外部模型或服务。

正式落地时至少需要考虑：

- 医生身份认证和最小权限控制；
- 患者身份确认和错配防护；
- 传输、存储和备份加密；
- 录音、病历和日志的保存期限；
- AI 草稿、医生修改和最终签名的版本区分；
- 访问和操作审计；
- 医生最终审核责任；
- 与医院信息安全、隐私保护和医疗软件监管要求的符合性。

## 评估指标

原型阶段建议关注以下指标，而不仅是文本是否通顺：

- 病程记录平均生成耗时；
- 医生平均修改比例；
- 关键事实遗漏率；
- 数值、单位、药物和时间错误率；
- 患者错配率；
- 无依据生成内容的发生率；
- 医生审核后的可接受率；
- 相比人工书写节省的时间。

## 贡献与后续方向

欢迎围绕以下方向继续完善：

- 接入真实或本地部署的医学语音识别；
- 增加说话人识别和医学术语纠错；
